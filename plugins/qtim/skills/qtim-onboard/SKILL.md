# qtim Onboard — глубокий онбординг dev-памяти

Setup делает быстрый discovery (5-10 tool calls) — этого хватает для charter, но `memory/` рождается тощей. Onboard — отдельный глубокий проход, чтобы команда не была «слепой» первые эпики.

Когда: после `$qtim-setup` на существующей кодовой базе, если инженерной памяти
ещё нет. Дрейф существующей памяти проверяет и исправляет `$qtim-kb-refresh`;
не запускай ради него полный onboard. Для greenfield-проекта он не нужен.
Продуктовый взгляд — зона `$qtim-product-onboard`.

Invocation of this skill is explicit permission to spawn the read-only researcher subagents described below.

Main task — qtim team-lead: используй `gpt-5.6-sol` + `ultra`. Если runtime exposes другой профиль, остановись до fan-out и попроси открыть новый task на Sol/Ultra; уже открытый task скрыто не переключай.

## Шаги

### 1. Инвентаризация

Прочитай `.codex/team-charter.md` (если нет — предложи `$qtim-setup` и остановись)
и индекс существующего `memory/`. Перед первой записью открой `$qtim-kb-format`.
Выдели только пробелы, существенные для ближайшей разработки; уже записанные
факты не собирай повторно. Для найденных устаревших anchors предложи
`$qtim-kb-refresh`, не пересоздавай память из отчётов исследователей.

### 2. План и бюджет

Покажи список исследуемых пробелов (подсистема -> что ищем) и объём fan-out.
Явный вызов скила уже разрешает исследование: работай в этом объёме без
дополнительного checkpoint. Начни с прямого чтения и точечных исследователей;
не поднимай роль на каждый каталог. Большой репозиторий — ядро сейчас,
периферия по потребности; существенное расширение scope верни владельцу.

### 3. Fan-out исследователей (read-only)

Параллельно в пределах доступных slots, built-in `explorer` на `gpt-5.6-luna` + `medium` / `worker` на подсистему, с чётким заданием на English; все follow-ups peer agents также пиши на English, а пользовательский итог и документы памяти — на Russian. Если исследователей больше cap, запускай batches и закрывай завершённые threads перед следующим:

- точки входа и карта модуля;
- реальные конвенции (именование, паттерны) с проверяемыми `path#Symbol`;
- инварианты, **соблюдаемые кодом** (не желаемые): владение данными, каскады, проверки доступа, переходы состояний;
- известные грабли (TODO/FIXME/workaround-комментарии, подозрительные обходы).

Исследователь возвращает структурированный вывод — в память сам не пишет.

### 4. Синтез (main thread)

Сведи только новые, подтверждённые и нужные факты в существующие файлы `memory/`
по layout из charter (`project-map.md`, `invariants.md`, `commands.md`, короткий
реестр указателей `decisions.md`, topic-файлы лишь по необходимости). Конфликт
между отчётами проверь сам по коду. Для каждого инварианта запиши устойчивый
`path#Symbol` и смысл, а не номер строки. Гипотезы помечай явно. При повторном
проходе обнови или удали опровергнутый факт вместо нового абзаца с поправкой.

### 5. Индекс и отчёт

Обнови `memory/MEMORY.md` только для реально существующих тем; пользователю —
что записано и какие существенные пробелы остались. Для будущего дрейфа назови
`$qtim-kb-refresh`.

## Правила

- Исследователи read-only: код не правят, в память не пишут — пишет только main thread (контроль дублей и качества).
- Не дублировать `AGENTS.md`/README — память дополняет их, не пересказывает.
- Инвариант без подтверждения в коде инвариантом не записывается.
- Объём: файлы памяти — сжатые факты, не эссе; один факт имеет один дом. Не
  сохраняй исследовательские отчёты и длинную историю проверки в точки входа.
- Повторный запуск обновляет существующие файлы памяти, а не создаёт дубли.
