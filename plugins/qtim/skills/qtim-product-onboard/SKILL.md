# qtim Product Onboard

Ты наполняешь **продуктовую** память проекта. Setup делает быстрый discovery — его хватает для charter, но роль `product` и конвейер `$qtim-feature` рождаются «слепыми»: intake и PRD опираются только на ответы пользователя. Этот skill — отдельный глубокий проход: собрать из кодовой базы (и опциональных материалов ПМа) карту продукта глазами пользователя.

Invocation of this skill is explicit permission to spawn the read-only researcher subagents described below. Production code не трогается, память пишет только main thread по `$qtim-kb-format`.

Main task — qtim team-lead: используй `gpt-6-astra` + `ultra`. Если runtime exposes другой профиль, остановись до fan-out и попроси открыть новый task на Astra/Ultra; уже открытый task скрыто не переключай.

## Когда

- Сразу после `$qtim-setup` с PM-дорожкой на существующей кодовой базе.
- Позже — для нового продуктового слоя, которого ещё нет в памяти. Дрейф уже
  записанных фактов обслуживает `$qtim-kb-refresh`.
- Для greenfield-проекта не нужен — нечего исследовать.

## Шаги

### 1. Инвентаризация

Прочитай `.codex/team-charter.md` (если нет PM-трека — предложи `$qtim-setup` и остановись), индекс существующего `memory/` (не дублировать уже записанное), `$qtim-kb-format` перед записью и, если существует, `docs/product-context/` — материалы ПМа. При устаревшем anchor или спорном факте предложи `$qtim-kb-refresh`, не используй полный onboard как перепроверку всей памяти.

### 2. План и бюджет

Покажи пробелы (линза → что ищем → где) и объём fan-out. Явный вызов скила
уже разрешает этот проход: не ставь повторный checkpoint перед чтением.
Начни с прямого чтения и точечных исследователей; не создавай агента на линзу
без субстрата. Для большого репозитория — ядро сейчас, периферия по
потребности; существенное расширение scope верни владельцу.

### 3. Fan-out исследователей (read-only)

Параллельно в пределах доступных slots, built-in `explorer` на `gpt-6-luna` + `medium` / `worker` под нужную линзу; prompts и follow-ups peer agents пиши на English, а пользовательский итог и документы памяти — на Russian. Если линз больше cap, запускай batches и закрывай завершённые threads перед следующим. Каждый возвращает структурированный вывод с проверяемыми `path#Symbol` и **в память сам не пишет**:

- **Разделы и экраны** — роутер/pages/навигация: какие user-facing разделы существуют, что пользователь может сделать в каждом, ключевые флоу (регистрация, основной сценарий, оплата). Выход: дерево разделов + флоу.
- **Акторы и права** — auth, роли, permissions, тенантность: кто есть в системе, кому что доступно, где проходит граница видимости. Выход: модель акторов + матрица прав.
- **Словарь домена** — схема БД/модели/типы: сущности и их связи бизнес-словами; поля-статусы и их переходы. Выход: глоссарий сущность → смысл для пользователя.
- **Аналитика и метрики** — вызовы трекинга (analytics/track/gtag/metrika и т.п.), фичефлаги, тарифные ограничения: какие события уже собираются, что за ними стоит. Выход: реестр событий + флагов.
- **Context-материалы** (только если `docs/product-context/` существует) — синтез материалов ПМа: боли из интервью/тикетов, цифры из выгрузок, каждый вывод со ссылкой на файл-источник.

Линзы без субстрата опускай (нет аналитики в коде — нет исследователя аналитики; скажи об этом в отчёте как о белом пятне).

### 4. Синтез (main thread)

Сведи отчёты в продуктовую память; конфликт между отчётами проверь сам по коду:

- `memory/product-map.md` — разделы, экраны, ключевые флоу;
- `memory/product-actors.md` — акторы, роли, права, границы видимости;
- `memory/product-glossary.md` — словарь домена;
- `memory/product-metrics.md` — события аналитики, фичефлаги, тарифные ограничения;
- выводы из context-материалов — туда же по смыслу, каждый со ссылкой на источник.

Каждый факт — с `path#Symbol` (или файлом-источником из product-context),
который подтверждает именно смысл; гипотезы помечай явно. Сжатые факты, не
эссе. Обновляй существующий факт на месте, опровергнутый удаляй, а не
дописывай историю поправок. `memory/MEMORY.md` индексирует лишь существующие
темы; не копируй туда их содержимое.

### 5. Отчёт

Что записано (по файлам), что осталось белым пятном (кандидаты на следующий проход или на вопросы к пользователю), и напоминание: `$qtim-feature` теперь будет опираться на эту память в intake/PRD, а метрики успеха PRD можно привязывать к реальным событиям из `memory/product-metrics.md`.

## Правила

- Исследователи read-only: код не правят, в память не пишут — пишет только main thread (контроль дублей и качества).
- Факт без подтверждения в коде или источнике фактом не записывается — помечай как гипотезу.
- Не дублировать `AGENTS.md`/README/dev-память — продуктовая память дополняет их, не пересказывает.
- Повторный запуск обновляет существующие `memory/product-*.md`, а не создаёт дубли.
- Один факт имеет один дом; продуктовый факт не копируй между несколькими файлами.
- Не смешивать с dev-памятью: инварианты кода и конвенции — зона обычного onboarding/dev-ролей, здесь — взгляд глазами пользователя и ПМа.
